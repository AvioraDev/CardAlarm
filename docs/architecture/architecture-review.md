# CardAlarm architecture review

**Reviewed:** 3 October 2026. **Source commit:** `09f44f230324467007bc70dbc61571b579386fd9`.

This is a repository-based review of the current web application, scanner, database contracts, matching, alerts, and operations. Read it alongside [System architecture](system-architecture.md) and [Build/runtime inventory](build-runtime-inventory.md). Recommendations describe proposed work; no application fixes or database changes were made for this review.

## Executive assessment

The overall shape is appropriate for an early product: a Next.js web application manages user intent, a separate worker gathers shared store inventory, and Postgres stores both durable work and derived results. Keeping customer watchlist changes on cached inventory is a particularly useful boundary. There is no architectural reason to replace this with microservices or a separate message broker now.

The immediate risks are contracts between these components, rather than the choice of framework. The committed profile policies do not protect the administrator role from its owner; a required classification table cannot be reconstructed from migrations; malformed successful ingestion responses can mark inventory unavailable; and several catalogue selections offered by the interface are not applied by matching. These should be addressed before treating the snapshot as ready for wider customer use.

The next priority is making matching and background work converge reliably. There are two implementations of watchlist matching and two alert senders, stale matches are retained by scan reconciliation, and the job lease does not fence off an old worker. Successful scan status also does not necessarily mean matching and notification processing succeeded. Existing unit checks are useful, but they do not exercise the actual PostgreSQL authorization and lifecycle boundaries where these problems reside.

## What is already working well

- **Useful separation of responsibilities.** Admin scan actions enqueue work; user watchlist actions backfill from cached products. The web request does not execute storefront scans. See [`web/src/lib/actions.ts:102`](../../web/src/lib/actions.ts#L102), [`web/src/lib/watchlist-actions.ts:16`](../../web/src/lib/watchlist-actions.ts#L16), and [`engine/src/worker.ts:75`](../../engine/src/worker.ts#L75).
- **Explicit user checks.** Server actions authenticate, watchlist mutations check ownership, and feedback writes validate that the target belongs to the user's available matches. Those checks complement RLS and matter because direct Postgres queries have a separate authorization boundary. See [`auth.ts:57`](../../web/src/lib/auth.ts#L57), [`watchlist-actions.ts:23`](../../web/src/lib/watchlist-actions.ts#L23), and [`actions.ts:28`](../../web/src/lib/actions.ts#L28).
- **Transactional batch persistence.** A fetched page writes source cache, canonical products, deterministic classifications, and availability events in a transaction, with stable product conflict keys. Watchlist backfill also deletes and rebuilds matches transactionally. See [`engine/src/db.ts:263`](../../engine/src/db.ts#L263) and [`watchlist-backfill.ts:38`](../../web/src/lib/watchlist-backfill.ts#L38).
- **Reasonable concurrency foundations.** Job and alert claims use `FOR UPDATE SKIP LOCKED`; enqueue creates the job and compatibility run in one transaction; store/page concurrency is bounded. There are heartbeat and stale-work recovery helpers. See [`scan-jobs.ts:45`](../../engine/src/scan-jobs.ts#L45), [`alerts.ts:222`](../../engine/src/alerts.ts#L222), [`web scan-jobs.ts:69`](../../web/src/lib/scan-jobs.ts#L69), and [`ingest.ts:80`](../../engine/src/ingest.ts#L80).
- **Some important safeguards exist.** Known incomplete or early-stopped ingestion does not reconcile missing inventory. The separate availability watchdog validates its payload and skips reconciliation after incomplete reads. Query timing logs use fingerprints rather than SQL parameters. See [`ingest.ts:417`](../../engine/src/ingest.ts#L417), [`availability.ts:31`](../../engine/src/availability.ts#L31), [`availability.ts:108`](../../engine/src/availability.ts#L108), and [`web db.ts:79`](../../web/src/lib/db.ts#L79).

## Prioritised findings

P1 means address before expanding use because it affects authorization, recoverability, inventory integrity, or the primary product contract. P2 means address next for correctness and reliable operation. Priorities describe engineering urgency, not a formal vulnerability score.

### F1 — P1: profile owners can satisfy the policy while changing their administrator role

**Status: verified policy defect; deployed exploitability conditional on effective grants and Data API exposure.** `profiles.role` permits `user` and `admin`. The owner UPDATE policy only requires that `user_id` remains the authenticated user's ID; the self-INSERT policy has the same ownership-only constraint. No committed role-column restriction or role-change trigger was found. Both server authorization and admin read policies trust that role.

**Trigger and consequence:** if an authenticated user has INSERT or UPDATE privilege covering `role`, an ordinary client can write `admin` to its own profile while satisfying RLS. The normal UI inserting `role: "user"` does not constrain a separate API client. That role then passes `requireAdmin`, exposing store management and scan controls and the database's admin-readable records. The SQL flaw is present even if current deployed grants happen to prevent exploitation.

**Evidence:** [`initial_schema.sql:13`](../../supabase/migrations/20260507000000_initial_schema.sql#L13), [`harden_cardalarm_rls_and_indexes.sql:54`](../../supabase/migrations/20260507001000_harden_cardalarm_rls_and_indexes.sql#L54), [`allow_profile_self_insert.sql:1`](../../supabase/migrations/20260507002000_allow_profile_self_insert.sql#L1), [`auth.ts:64`](../../web/src/lib/auth.ts#L64), [`store-actions.ts:27`](../../web/src/lib/store-actions.ts#L27). The later consolidation migration removes old policies but leaves these modern policies in place: [`consolidate_user_owned_rls_policies.sql:13`](../../supabase/migrations/20260513005000_consolidate_user_owned_rls_policies.sql#L13).

**Recommendation:** make role assignment an explicitly privileged operation. Separate role membership from editable profile data or restrict client column privileges and enforce the initial role. Verify effective grants, policies, and role-change controls together; protect both INSERT and UPDATE. Preserve legitimate display-name editing and initial profile creation.

### F2 — P1: migrations do not create a table required by the active runtime

**Status: verified repository completeness defect; live schema unknown.** No committed migration creates `public.product_classifications`. Its index and RLS migrations explicitly skip work when the table does not exist; one describes it as an existing remote table. Active ingestion nevertheless inserts into it and matching/read queries join it.

**Trigger and consequence:** a fresh environment built only from the committed migrations lacks this runtime contract. Its first product batch fails, and classification-dependent inventory/backfill queries fail. An existing hosted table can conceal the problem, but a clean staging setup or recovery from code alone cannot reproduce that state.

**Evidence:** [`product_classifications_rls.sql:1`](../../supabase/migrations/20260513003000_product_classifications_rls.sql#L1), [`product_classifications_rls.sql:29`](../../supabase/migrations/20260513003000_product_classifications_rls.sql#L29), [`baseline_performance_indexes.sql:43`](../../supabase/migrations/20260513002000_baseline_performance_indexes.sql#L43), [`engine/src/db.ts:411`](../../engine/src/db.ts#L411), [`watchlist-reconciliation.ts:39`](../../engine/src/watchlist-reconciliation.ts#L39).

**Recommendation:** capture and review the canonical table definition, unique key used by upserts, foreign keys, grants, policies, indexes, and update behavior in versioned migrations. Prove that a fresh disposable database can apply all migrations and execute a representative ingest/read/backfill cycle. Compare the hosted schema separately to identify additional drift; do not invent its definition from application fields alone.

### F3 — P1: malformed successful ingestion responses can clear available inventory

**Status: verified control flow; no live store response reproduced.** The ingestion fetcher casts JSON to a type and evaluates `data.products ?? []`. An HTTP 200 body such as `{"error":"temporarily unavailable"}` therefore becomes a legitimate empty page. No fetch error is recorded, so post-scan missing-product reconciliation is allowed.

**Trigger and consequence:** a malformed first-page response can mark all previously available products for that source unavailable; a malformed later page can mark unseen products unavailable. This also creates misleading sold-out events. The separate watchdog has validation, but that protection does not cover ingestion.

**Evidence:** [`ingest.ts:194`](../../engine/src/ingest.ts#L194), [`ingest.ts:217`](../../engine/src/ingest.ts#L217), [`ingest.ts:344`](../../engine/src/ingest.ts#L344), [`ingest.ts:417`](../../engine/src/ingest.ts#L417), [`db.ts:664`](../../engine/src/db.ts#L664). Compare the validated watchdog at [`availability.ts:31`](../../engine/src/availability.ts#L31).

**Recommendation:** share a validated storefront response contract across both readers. Distinguish a valid empty array from a missing or malformed inventory field, and require positive evidence of a complete scan before destructive absence reconciliation. Preserve inventory on uncertainty and report incomplete scans explicitly.

### F4 — P1: catalogue selections are stored but do not constrain matching

**Status: verified end-to-end source contract mismatch.** The form presents catalogue team, set, card, and variant choices and says catalogue fields are preferred. The action persists their IDs and `intent_type`. The active reconciliation and backfill predicates do not use those fields. They use player ID and text/flag/price filters. In addition, an empty include-terms input normally becomes the watchlist name, even when catalogue intent was selected.

**Trigger and consequence:** selecting one catalogue card does not make matching specific to that card. Changing a set/card/variant selection while keeping other filters constant has no matching effect. Naming a catalogue watchlist “My favourites” can accidentally require that text in product data, hiding otherwise relevant cards. The interface can therefore promise precision that the engine does not provide.

**Evidence:** [`watchlist-form-fields.tsx:98`](../../web/src/app/watchlists/watchlist-form-fields.tsx#L98), [`watchlist-actions.ts:60`](../../web/src/lib/watchlist-actions.ts#L60), [`watchlist-actions.ts:82`](../../web/src/lib/watchlist-actions.ts#L82), [`watchlist-reconciliation.ts:35`](../../engine/src/watchlist-reconciliation.ts#L35), [`watchlist-reconciliation.ts:54`](../../engine/src/watchlist-reconciliation.ts#L54), [`watchlist-backfill-sql.ts:1`](../../web/src/lib/watchlist-backfill-sql.ts#L1), [`watchlist-backfill-sql.ts:112`](../../web/src/lib/watchlist-backfill-sql.ts#L112).

**Recommendation:** define one supported rule contract and implement catalogue constraints against a trustworthy product identity projection. Validate card/set/player/variant relationships, not just individual ID existence. Keep display names separate from matching terms. Until identity-backed matching is implemented, make the interface accurately describe the supported filters rather than implying that saved catalogue IDs are effective.

### F5 — P2: minimum confidence raises the recorded score instead of filtering results

**Status: verified SQL semantics.** Both matching implementations calculate `greatest(coalesce(pcm.confidence, 0), minimum_match_confidence)` and store that value. Neither requires actual confidence to meet the minimum; classification confidence is not used in that expression.

**Trigger and consequence:** a text-matching product with no `product_card_matches` row can receive the user-entered minimum, such as 0.95, as its apparent confidence and be marked `current`. A low-confidence legacy match can likewise be raised. Alert payloads and feed ordering consume these scores, so increasing the requested threshold can inflate apparent certainty without improving selection.

**Evidence:** [`watchlist-reconciliation.ts:26`](../../engine/src/watchlist-reconciliation.ts#L26), [`watchlist-backfill-sql.ts:167`](../../web/src/lib/watchlist-backfill-sql.ts#L167), [`watchlist-backfill-sql.ts:192`](../../web/src/lib/watchlist-backfill-sql.ts#L192), [`alerts.ts:173`](../../engine/src/alerts.ts#L173).

**Recommendation:** separate observed evidence confidence, rule threshold, and rule-satisfaction status. Apply the threshold as a predicate against a defined evidence score. Preserve unscored states and make legacy identity precedence explicit. Test missing, low, and high evidence independently of the user-entered threshold.

### F6 — P2: matching does not converge consistently after inventory changes

**Status: verified implementation divergence.** Scan reconciliation inserts or updates qualifying matches but never removes/invalidates rows that no longer qualify. Web backfill deletes and rebuilds a watchlist's matches. The two predicate sets also differ: engine graded/raw matching recognises `PSA`/`BGS`, while web backfill uses `graded`; the engine accepts classification card number directly, while the web predicate checks title/description patterns.

**Trigger and consequence:** a product matched below a maximum price can remain in “My Matches” after its price rises above that limit, as long as it is still active/available. A manual refresh can remove it. A graded rule can also produce different results after a scan and a manual refresh. Alert candidate selection trusts the stored rows rather than rechecking rule qualification.

**Evidence:** [`watchlist-reconciliation.ts:128`](../../engine/src/watchlist-reconciliation.ts#L128), [`watchlist-reconciliation.ts:132`](../../engine/src/watchlist-reconciliation.ts#L132), [`watchlist-backfill.ts:41`](../../web/src/lib/watchlist-backfill.ts#L41), [`watchlist-backfill-sql.ts:143`](../../web/src/lib/watchlist-backfill-sql.ts#L143), [`watchlist-backfill-sql.ts:162`](../../web/src/lib/watchlist-backfill-sql.ts#L162), [`inventory-sql.ts:4`](../../web/src/lib/inventory-sql.ts#L4), [`alerts.ts:177`](../../engine/src/alerts.ts#L177).

**Recommendation:** use one rule evaluator or SQL generator for immediate and background reconciliation. Treat matches as a versioned derived projection with explicit invalidation of non-qualifying rows. Reconcile changed products and changed rules transactionally; require identical result sets for web and worker paths on shared fixtures.

### F7 — P2: job claiming does not prevent overlapping scans or stale-owner writes

**Status: verified missing coordination; impact conditional on concurrency/recovery.** `SKIP LOCKED` prevents simultaneous claims of the same queued row. It does not exclude two different jobs scanning the same stores. The web active-job check occurs before the enqueue transaction, with no active-job uniqueness constraint. The cron entrypoint also runs ingestion independently. Stale recovery releases a job, but heartbeats returning zero do not stop the old worker. Completion updates the compatibility `scan_runs` row even if the owner-checked job update affected zero rows.

**Trigger and consequence:** concurrent admin requests, a cron/worker overlap, or a worker resuming after lease expiry can overlap scans. Since absence reconciliation compares a single mutable `last_seen_scan_token`, another run can overwrite that token and make an observed product appear missing to the first run. An obsolete worker can also publish a misleading completed run projection.

**Evidence:** [`actions.ts:108`](../../web/src/lib/actions.ts#L108), [`web scan-jobs.ts:69`](../../web/src/lib/scan-jobs.ts#L69), [`scan_job_queue.sql:76`](../../supabase/migrations/20260513008000_scan_job_queue.sql#L76), [`index.ts:32`](../../engine/src/index.ts#L32), [`worker.ts:65`](../../engine/src/worker.ts#L65), [`scan-jobs.ts:109`](../../engine/src/scan-jobs.ts#L109), [`scan-jobs.ts:215`](../../engine/src/scan-jobs.ts#L215), [`db.ts:664`](../../engine/src/db.ts#L664).

**Recommendation:** route scheduling through one queue producer and enforce the chosen single-active-run or per-store exclusivity rule atomically. Introduce a claim generation/lease token and verify it before publishing state and reconciling absence. On lease loss, abort work. Update job and compatibility projection in one transaction only after a successful owner check. Per-store jobs need not be implemented merely to achieve this guarantee.

### F8 — P2: alert eligibility and delivery lifecycle are incomplete

**Status: verified source behavior; actual duplicate/lost delivery not observed.** Pending claims check only alert status, time, and attempt count. They do not recheck notification preference, watchlist activity, current availability, or whether the original match still qualifies. Disabling notifications updates the watchlist but does not suppress pending alerts. The duplicated web/engine senders lack an explicit request deadline and provider idempotency key. `off` and `log` modes return success and are subsequently recorded as `sent`.

**Trigger and consequence:** an alert queued while enabled can still send after the user disables notifications or the product becomes irrelevant. A crash after provider acceptance but before the database update can cause a retry to send twice. A hanging send can hold a claimed batch and, in the web path, a user action open. Running with `off` or default `log` can consume deduplicated notifications without real delivery; enabling delivery later does not replay rows already marked sent.

**Evidence:** [`watchlist-actions.ts:194`](../../web/src/lib/watchlist-actions.ts#L194), [`engine alerts.ts:89`](../../engine/src/alerts.ts#L89), [`engine alerts.ts:113`](../../engine/src/alerts.ts#L113), [`engine alerts.ts:222`](../../engine/src/alerts.ts#L222), [`engine alerts.ts:249`](../../engine/src/alerts.ts#L249), [`web alerts.ts:287`](../../web/src/lib/alerts.ts#L287).

**Recommendation:** centralise alert processing in a durable worker, with web requests enqueueing only. Recheck eligibility immediately before send, use an explicit claim token/deadline, and use the provider's supported idempotency contract. Represent simulated/suppressed delivery separately from sent delivery. Keep the current lifetime dedupe policy only if “one new-match email per product/watchlist” is the intended product behavior; restock events are a separate feature.

### F9 — P2: operational success and configured behavior exceed what the worker guarantees

**Status: verified runtime gaps; deployed scheduling and monitoring unknown.** The worker loop consumes queued jobs but does not create scheduled ones. `scan_frequency_minutes` is stored/displayed but not selected by source loading or used in scheduling. The separate cron entrypoint scans every 15 minutes. Scan `mode` does not override the store's `scanStrategy`; a `full` job can still early-stop for an incremental store. A partial fetch failure is considered a successful source if any products were fetched, and reconciliation/alert errors are caught and logged without failing the scan job.

**Trigger and consequence:** a worker-only deployment without another producer does not automatically scan at the configured store interval. An operator can request “full,” receive early-stop behavior, or see completion despite partial inventory/matching failure. Retried alerts advance only when another processing pass is triggered. The queue schema's cancellation and per-store helpers are not wired into the executing scan loop, so their presence should not be interpreted as working cancellation or per-store retries.

**Evidence:** [`worker.ts:144`](../../engine/src/worker.ts#L144), [`sources.ts:101`](../../engine/src/sources.ts#L101), [`index.ts:35`](../../engine/src/index.ts#L35), [`ingest.ts:162`](../../engine/src/ingest.ts#L162), [`ingest.ts:427`](../../engine/src/ingest.ts#L427), [`ingest.ts:485`](../../engine/src/ingest.ts#L485), [`ingest.ts:553`](../../engine/src/ingest.ts#L553), [`scan-jobs.ts:257`](../../engine/src/scan-jobs.ts#L257).

**Recommendation:** define and test a small operational state machine: complete, incomplete, failed, cancelled, and lease-lost; distinguish inventory success from matching/delivery success. Make full mode and configured cadence real or remove those promises. Implement one scheduler, independent alert retry processing, and actionable health metrics. Expose unsupported controls as planned capability in documentation.

## Architecture tradeoffs and additional gaps

| Choice | Benefit | Constraint and next decision |
| --- | --- | --- |
| One Postgres database for queue, inventory, identity, and user data | Simple transactions, deployment, and inspection | Workload isolation and query budgets matter. Keep this design; use distinct least-privilege web/worker database roles where feasible. Direct `pg` connections do not acquire the user's Supabase JWT automatically. Effective role/RLS behavior must be verified. See [`web db.ts:95`](../../web/src/lib/db.ts#L95). |
| Shared cached inventory plus derived watchlist matches | Customer actions avoid storefront traffic | Define provenance, rule/classifier versions, invalidation, and replay contracts so the projections remain trustworthy. Current ingest uses deterministic classification/reconciliation; the older `match.ts` identity matcher is not invoked by it. See [`ingest.ts:11`](../../engine/src/ingest.ts#L11), [`ingest.ts:355`](../../engine/src/ingest.ts#L355). |
| Incremental early-stop scans | Reduces storefront and database work | Unchanged leading pages do not prove later inventory is unchanged. Schedule periodic proven-complete scans, measure freshness per store, and preserve the existing no-absence-reconciliation rule for early stops. No actual freshness SLA was established. |
| Product-level identity with first variant price/availability | Fits stores selling a single card per product | Both ingest and watchdog inspect `variants[0]`. Confirm that this is a supported-store invariant; otherwise define variant aggregation/identity. Currency is configurable on a source but is not carried in the ingestion cache input, and the canonical insert relies on the NZD schema default. Restrict supported currency or propagate and compare it explicitly. See [`ingest.ts:244`](../../engine/src/ingest.ts#L244), [`availability.ts:77`](../../engine/src/availability.ts#L77), [`db.ts:353`](../../engine/src/db.ts#L353), [`initial_schema.sql:66`](../../supabase/migrations/20260507000000_initial_schema.sql#L66). |
| Two separate npm projects and direct TypeScript worker execution | Straightforward local development | Shared contracts currently drift across packages. Extract a small tested common domain/SQL module before a broad monorepo restructure. Pin supported Node/package-manager versions and make root inference explicit. See [inventory](build-runtime-inventory.md). |
| Append-only feedback and availability history | Useful audit and diagnostic evidence | Define retention, backup/restore, privacy-aware logging, and expected event volume. Alert log mode records recipient and message content; access/retention controls need deployment evidence. Store admin actions do not write to the existing audit-log table. See [`engine alerts.ts:96`](../../engine/src/alerts.ts#L96), [`store-actions.ts:27`](../../web/src/lib/store-actions.ts#L27). |

**Performance:** global reconciliation joins all active rules against available products with lateral identity/classification lookups and text predicates. Page caching also recomputes/upserts classification for fetched products before deciding which were unchanged. Customer feeds are not paginated, and stats/facets execute several related aggregate queries. These are measurable scaling risks, not demonstrated current bottlenecks. Capture production-like row counts and `EXPLAIN (ANALYZE, BUFFERS)` before changing indexes. Prefer changed-product reconciliation, paginated customer feeds, and consolidated aggregates before introducing infrastructure. Evidence: [`watchlist-reconciliation.ts:35`](../../engine/src/watchlist-reconciliation.ts#L35), [`db.ts:270`](../../engine/src/db.ts#L270), [`queries.ts:50`](../../web/src/lib/queries.ts#L50), [`queries.ts:83`](../../web/src/lib/queries.ts#L83), [`queries.ts:164`](../../web/src/lib/queries.ts#L164).

**Input and transaction integrity:** card number is free text but concatenated into a PostgreSQL regex. SQL parameters prevent SQL injection; they do not escape regex metacharacters. A malformed expression can fail a matching statement, including the all-watchlist reconciliation. Treat card numbers as literal structured values or escape them. Watchlist creation and rule creation are separate requests, and update similarly spans separate writes, so a rule failure can leave a partial user-visible mutation. Make each logical change atomic and let backfill run as retriable derived work. Evidence: [`watchlist-form.ts:133`](../../web/src/lib/watchlist-form.ts#L133), [`watchlist-backfill-sql.ts:149`](../../web/src/lib/watchlist-backfill-sql.ts#L149), [`watchlist-reconciliation.ts:121`](../../engine/src/watchlist-reconciliation.ts#L121), [`watchlist-actions.ts:47`](../../web/src/lib/watchlist-actions.ts#L47).

**Testing:** the suite includes real deterministic parsing/classification checks, but many SQL/security tests check source text or use mocked database calls, and older matching tests exercise the SQLite implementation. Passing these tests cannot establish PostgreSQL syntax, effective RLS/grants, migration completeness, or agreement between current matching paths. No checked-in CI workflow or database integration test directory was found. Add targeted boundary tests, not more assertions that implementation strings are present. Evidence: [`match.test.ts:1`](../../engine/__tests__/match.test.ts#L1), [`watchlist-backfill-sql.test.ts:40`](../../engine/__tests__/watchlist-backfill-sql.test.ts#L40), [`product-classifications-rls.test.ts:4`](../../engine/__tests__/product-classifications-rls.test.ts#L4), [`server-action-security.test.ts:1`](../../engine/__tests__/server-action-security.test.ts#L1).

**Operations and dependencies:** no deployed host, supervision/restart policy, scheduler, backup restoration result, alert-provider configuration, or service objectives were verified. Triage the audit findings recorded in the inventory using actual dependency paths and runtime exposure, then upgrade deliberately. A raw critical/high count does not by itself establish exploitability. Verify TLS certificate checking in deployment; the source permits explicit opt-out for local troubleshooting. The remote-font build dependency and multiple-lockfile warning are reproducibility improvements after the correctness work, not reasons to rewrite the application.

## Phased improvement plan and acceptance evidence

| Phase | Scope | Concrete acceptance criteria |
| --- | --- | --- |
| **0 — establish a safe, reproducible baseline** | F1, F2, F3; pin test environment | On a fresh disposable Supabase/Postgres instance, all migrations apply and a sample ingest/read/backfill succeeds. Authenticated owner INSERT/UPDATE cannot assign `admin`; ordinary profile edits work; another user's row is denied. Ingest HTTP 200 `{}`, `null`, missing/invalid products, and a malformed later page all preserve prior availability and record incomplete failure. A genuine complete empty inventory follows the documented absence policy. Run these in CI alongside current checks. |
| **1 — make user intent accurate** | F4–F6; literal input validation; atomic watchlist writes | Shared fixtures prove team/set/card/variant choices change eligibility correctly, incompatible catalogue relationships are rejected, and display-name changes do not change matching. A failed rule write leaves no partial watchlist update. |
| **2 — make background work recover predictably** | F7–F9; central alert sender | Concurrent enqueue/worker tests prove the chosen per-store exclusivity rule. Full mode reaches inventory end; due-time scheduling respects configured cadence; partial fetch and matching failures produce actionable status. Provider-accepted/database-update-failed retries use one logical delivery key. Disabling notifications or invalidating a pending match prevents its send. Phases describe dependency order rather than calendar estimates. Keep the current monolith-plus-worker topology while these contracts stabilise; extract additional services only for a measured ownership, scale, or isolation need.

## Questions requiring deployment or product evidence

1. What INSERT/UPDATE column privileges does `authenticated` actually have on `profiles`, and are there out-of-repository role-protection triggers? Which database roles do web and worker URLs use, and do they bypass RLS?
2. What is the hosted definition of `product_classifications`, and what other schema/grant differences exist from a clean migration reset?
3. Which processes actually run: cron engine, queue worker, or both? What produces scheduled jobs, prevents overlap, restarts failed workers, and drains alert retries?
4. Is each supported store guaranteed to use one relevant variant and NZD? What freshness and full-inventory cadence does the product promise?
5. Should alerts include possible/unscored matches, or only threshold-qualified evidence? Should a restock generate another alert after the original new-match notification?
6. What are current row counts, request/scan latency, connection limits, oldest queued work, failure rates, and tested backup recovery time? What retention applies to product payloads, email logs, and feedback?
7. Which dependency advisories are reachable in the deployed application, and what versions/configuration actually ship? The repository audit totals alone cannot answer this.

Older notes capture useful history but contain obsolete assertions: `auth-and-user-isolation.md` still describes dashboard reads from legacy tables and watchlists as future work; `db-backed-scan-jobs-phase-1-2.md` says there is no worker loop or store parallelism; `engine-runtime-supabase.md` describes a legacy watchlist fallback that is not the current ingestion path. `target-scan-engine-pipeline.md` is a target design, not evidence that per-store scheduling, cancellation, or all queue behaviors are implemented. The current architecture must distinguish deterministic title classification, optional legacy identity rows, and catalogue intent that is saved but not yet enforced.
